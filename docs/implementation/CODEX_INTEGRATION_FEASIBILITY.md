## Official integration surfaces

### Codex lifecycle hooks — OFFICIALLY SUPPORTED

Hooks are documented, enabled, and marked stable in the installed CLI. They run
commands at lifecycle boundaries and receive JSON on standard input. They can
be configured at user or project scope. This is the only investigated official
surface that passively delivered lifecycle events from a session owned by the
normal CLI.

### Codex App Server — DOCUMENTED BUT LIMITED for passive capture

App Server is an official JSON-RPC interface over standard I/O by default, with
experimental Unix-socket and WebSocket transports exposed by the installed
binary. The CLI labels the `app-server` command experimental. Its schema includes
threads, turns, typed items, command status/output, file changes, errors,
interruptions, approvals, and streaming notifications.

The supported `thread/list` and `thread/read` methods can inspect persisted
threads without starting or resuming them. That enables passive **snapshot
polling** of an independently started CLI thread. App Server did not provide a
way to subscribe to live events from that externally owned thread. Calling
`thread/start` or `thread/resume` makes the App Server client participate in and
control the conversation, which is a different product experience.

### Direct local session storage — UNDOCUMENTED / INTERNAL

The installation had session JSONL files, indexes, and SQLite databases with
thread-related tables. No official stable direct-reader contract was found. The
official way to read persisted threads is App Server. Direct filesystem or
database parsing would couple Mochi to private storage layouts, concurrency
behavior, migrations, and data that may be broader than the user consented to
share. It is not a V1 integration candidate.

### Git observation — OFFICIALLY SUPPORTED supplemental source

Git is independent of Codex and deterministically reports repository state. It
does not report prompts, reasoning, commands, reads, tests, approvals, or session
boundaries. It is valuable as corroboration and as a final source of exact code
changes, not as session telemetry.

## Hooks investigation

### Installation and trust behavior

The official configuration locations include user-level and project-level
`config.toml` and `hooks.json`. User-level hooks are sufficient to cover projects
without modifying every repository; a production installer would still need to
merge configuration safely and preserve user-owned entries. Project hooks only
run for a trusted project.

The controlled probe used `.codex/hooks.json` in the synthetic repository. On
first launch, Codex listed the exact command under each configured hook category
and required review in `/hooks`. The test used that normal UI and did not pass a
trust-bypass flag. Unrelated definitions were left untrusted. Codex skipped the
probe until it was trusted. An identical definition remained trusted on the next
launch. Renaming the hook file disabled the probe cleanly: a subsequent launch
added no probe start or end records. Updating and revoking retained trusted
hashes were not tested and belong in Brief 01B.

`/hooks` is the user-visible verification surface. A viable “Connect Codex” flow
must explain that Codex, rather than Mochi, asks the user to trust an exact local
hook command. Mochi must never bypass that decision.

### Actual payloads

The logger emitted no standard output or error, capped input and record sizes,
redacted common credential patterns and sensitive keys before its first durable
write, replaced identifying paths, and wrote mode `0600` files only beneath the
synthetic temp root. It is deliberately a diagnostic sanitizer, not the product
sanitizer specified by Mochi security policy.

All observed payloads contained `session_id`, `transcript_path`, `cwd`, and
`hook_event_name`. Turn-scoped events also carried `turn_id`, `model`, and
`permission_mode`. The official documentation explicitly says the transcript
path format is not a stable hook interface, so Mochi must ignore it.

| Hook | Observed payload beyond the common fields | Result |
| --- | --- | --- |
| `SessionStart` | `source`, `permission_mode`, `model` | Observed once per tested CLI launch. The source was present; its value is omitted because the product mapping should not depend on an undocumented enum. |
| `UserPromptSubmit` | `turn_id`, `prompt` | Full synthetic prompt was available before execution. |
| `PreToolUse` | `turn_id`, `tool_name`, `tool_use_id`, `tool_input` | Shell and patch tools were observed. Inputs contained command or patch content and paths. |
| `PermissionRequest` | `turn_id`, `tool_name`, `tool_input` | Fired before the normal edit approval prompt was accepted. It had no `tool_use_id`, so correlation is by turn, tool, input fingerprint, and a short time window. |
| `PostToolUse` | `turn_id`, `tool_name`, `tool_use_id`, `tool_input`, `tool_response` | Paired exactly with completed tool calls. Shell response text exposed controlled failure and success output. No structured shell exit-code field was present. |
| `Stop` | `turn_id`, `stop_hook_active`, `last_assistant_message` | Supplied the final assistant text for completed turns. It did not provide a general structured completion-status field. |
| `Interrupt` | `turn_id`, `permission_mode` | Fired when Escape interrupted a running `sleep` command. No matching `PostToolUse` arrived for that command. |
| `SessionEnd` | `reason` | Fired on `/exit`. The observed reason was `other`, consistent with the documented currently coarse reason field. It had no model, turn, or permission field. |

The probe recorded 26 hook deliveries across the main and permission sessions:
two `SessionStart`, four `UserPromptSubmit`, seven `PreToolUse`, one
`PermissionRequest`, six `PostToolUse`, three `Stop`, one `Interrupt`, and two
`SessionEnd`. Six completed tool calls paired by `tool_use_id`; the interrupted
command left one unmatched start, which is useful gap/cancellation evidence.

The documented lifecycle also includes `PreCompact`, `PostCompact`,
`SubagentStart`, and `SubagentStop`. Those can help detect context compaction and
subagent boundaries, but they were not triggered locally, so their local fidelity
is only `PARTIAL` in this report. Hosted web search and other specialized tool
paths may opt out of general tool hooks according to the documentation.

## App Server investigation

The probe launched:

```text
codex app-server --listen stdio://
```

It performed the required `initialize`/`initialized` handshake and used exact
working-directory filtering with `thread/list`, followed by `thread/read`. It
inherited the installed Codex authentication state and required no new login.
The diagnostic client printed only field names, statuses, counts, typed change
kinds, durations, exit codes, and hashes of identifiers; it suppressed prompts,
responses, commands, output, paths, diffs, names, and account data.

The generated 0.151.0 protocol contains:

- stable thread list/read/start/resume methods and experimental paginated
  alternatives;
- thread identity, working directory, CLI version, source, timestamps, status,
  Git information, and turns;
- turn start/completion and item start/completion notifications;
- typed user and agent messages, reasoning, command execution, file change, and
  MCP items;
- command output deltas, exit codes, duration, status, and parsed command
  actions;
- file-change lists and diff notifications;
- approval requests, errors, and interruption/completion status.

While the independent CLI was active, App Server found the thread by its exact
synthetic working directory and read the already persisted completed turn. The
thread source was `cli`; the CLI version was 0.151.0; Git information was
present. App Server reported the thread as `notLoaded` even while the external
CLI was active. This shows that status describes whether the thread is loaded in
that App Server process, not whether another client currently has it open.

After the CLI session, the same read contained three hydrated turns. It reported
the simple turn as completed; the coding turn as completed with an exit-0
inspection command, an exit-1 test command, one typed file-change item covering
add/update/delete operations, an exit-0 verification command, and agent/reasoning
items; and the interrupted turn as interrupted with a failed command item,
exit code `-1`, and duration. This representation was more structured than hook
payloads.

`thread/read` with full turns also emitted a deprecation notice in 0.151.0, while
the replacement paginated read methods were marked experimental in the generated
schema. Combined with the experimental CLI entrypoint and lack of live attachment
to an external thread, this is not a sufficiently stable primary V1 capture path.

### Critical existing-session answer

**App Server can passively list and poll persisted snapshots of an independently
started CLI session. It cannot subscribe to that external session's live event
stream through an observed or documented attachment method.** Starting or
resuming a thread through App Server changes the relationship: Mochi then owns or
participates in the Codex client session. Polling can support diagnostics or
reconciliation, but it cannot by itself establish reliable live start/end
semantics. Independently started Desktop-session visibility remains unproven.

## Reliability findings

| Scenario | Observed result |
| --- | --- |
| A — simple request | Prompt and final assistant response were captured. No false tool event appeared. App Server later represented one completed user/agent turn. |
| B — file edit | Patch start/result identified a modified source file, dependency update, new notes file, and deletion. Git independently confirmed final add/modify/delete state. |
| C — command execution | Shell start/result exposed the exact synthetic command and output. App Server supplied structured status, exit code, and duration. |
| D — failure and recovery | The first unit test failed, the patch fixed the bug, and the second test passed. Hooks exposed both outputs but required parsing; App Server represented exit 1 then exit 0. |
| E — interrupt | Escape emitted `Interrupt`. The running command had `PreToolUse` but no `PostToolUse`. App Server later marked the turn interrupted and command failed with exit code -1. |
| F — normal completion | `/exit` emitted `SessionEnd`; its reason was only `other`. |
| G — Desktop | Not executed. Desktop hook and persisted-thread behavior remain unknown. |
| H — CLI | Executed on 0.151.0. All core scenarios and explicit permission flow were observed without launching from Mochi. |

Hooks are at-least-observable rather than proven exactly-once delivery. A crash,
force kill, machine sleep, bounded async queue overflow, hook timeout, malformed
payload, or session-end cancellation can create gaps. Background hooks can finish
out of order, have a documented per-session concurrency bound, and may be
cancelled when the session ends. `SessionEnd` is synchronous even when configured
as asynchronous. Production events therefore need source event IDs where
available, deterministic deduplication, bounded reordering, unmatched-start
timeouts, and explicit `capture.gap` records.

The session identifier and turn identifier were stable across related hook
events. Completed tool calls correlated by `tool_use_id`. The permission event's
missing tool-use identifier is a concrete ambiguity. Session-end reason and hook
tool result structure are too coarse to use without inference.

Git attribution also requires an initial snapshot. The experiment deliberately
made one file dirty before Codex started; comparing the initial and final state
preserved that distinction. A final `git diff` alone would wrongly attribute the
pre-existing change to Codex. Concurrent user edits remain inherently ambiguous
and must be reported as such unless a provider event corroborates them.

## Privacy findings

Hooks can expose the full user prompt, final assistant response, command text,
command output, patch content, filesystem paths, repository names, and tool
inputs/results. Those fields can contain source code, environment values, tokens,
credentials, or secrets printed by a command. Hook execution itself runs a local
command outside the model's sandbox, so its executable path and arguments are a
security-sensitive trust decision.

App Server can expose still richer conversation, reasoning, command, output,
diff, approval, repository, and account-adjacent metadata. Polling the global
thread list without an exact project allowlist could reveal unrelated work. A
future probe must scope reads by a consented repository and session identity.

Direct local storage has the broadest accidental-access risk because it may mix
many repositories and historical conversations. Its unsupported nature also
makes reliable minimization difficult. It should not be read by Mochi V1.

Git exposes repository paths, branches, source diffs, untracked files, and
potential secrets already present in the worktree. Even without prompts, a diff
can be highly sensitive.

For every candidate path, recognizable secrets must be removed in memory before
the first durable write. The capture helper must minimize fields before local
persistence, bound and sanitize diagnostics, never inherit more environment than
required, and sanitize again before remote analysis and after model output. A
sanitizer failure must drop/quarantine the event and emit only safe gap metadata.
Local capture consent and remote analysis consent remain separate.

## Performance findings

Codex executes normal hooks synchronously unless they are configured as
background hooks. The measured Python probe's own processing and append section
had a 0.319 ms median and 0.902 ms maximum across 26 records, but those numbers
exclude interpreter startup. Thirty full subprocess executions measured 40.34 ms
minimum, 41.75 ms median, 42.55 ms sample p95, and 43.94 ms maximum. Repeating
that synchronous cost around every tool call would be noticeable in a busy turn.

Production capture should point hooks at one minimal, signed Rust helper that
performs bounded validation, in-memory secret removal, and a non-blocking handoff
to a local Mochi process. It should avoid Python startup and synchronous `fsync`
per event. Brief 01B must benchmark the real helper at p50/p95/p99 and under burst
and disconnected-daemon conditions. Background delivery is suitable for most
events only if Mochi accepts reordering and session-end cancellation; the helper
invoked by synchronous `SessionEnd` must still return quickly.

App Server polling starts another local Codex process, reads persisted thread
state repeatedly, and may hydrate growing histories. It was responsive in this
small probe, but no sustained-load benchmark was run. Git status/diff scales with
repository size, ignored files, untracked files, and filesystem performance; it
must run at bounded checkpoints rather than on every hook event.

## Mochi event mapping

This is a proposed adapter mapping to the existing canonical schema. It does not
change that schema.

| Codex/Git evidence | Mochi event | Mapping confidence and rule |
| --- | --- | --- |
| `SessionStart` | `session.started` | Direct. Use hook `session_id`, receive time, sanitized `cwd`, and separately resolved Git identity. Do not consume `transcript_path`. |
| `UserPromptSubmit` | `user.prompt` | Direct. Sanitize before persistence; use `turn_id`. |
| `PreToolUse` | `tool.started` | Direct for hooked tools. Preserve provider tool name only in sanitized metadata and use `tool_use_id` as source ID. |
| `PostToolUse` | `tool.completed` | Direct completion boundary; outcome is `unknown` unless a safe tool-specific parser establishes success/failure. |
| Shell `PreToolUse` | `command.executed` | Direct command observation after sanitization. Use an argument representation only when it can be parsed without shell execution. |
| Shell `PostToolUse` | `command.result` | Partial. Preserve bounded sanitized output; hook payload did not supply a structured exit code. |
| Recognized test command plus result | `test.result` | Inferred. Emit only when a deterministic command classifier recognizes the runner; retain `confidence=inferred`. |
| Failed tool/command evidence | `error.observed` | Inferred from safe parsing, explicit App Server status, or missing completion timeout. Do not infer from prose alone. |
| Later successful action after failure | `recovery.attempted` | Inferred correlation within the turn, with evidence references to both events. |
| Patch-tool fields | `file.changed` | Partial provider-reported change. Confirm final kind and exact diff with pre/post Git snapshots. |
| Pre/post Git snapshot | `file.changed` | Direct repository-state evidence, but attribution is `observed_during_session`; preserve pre-existing dirty state and ambiguity. |
| Git diff/stat | `git.snapshot` | Direct sanitized snapshot/reference at bounded boundaries. Include repository identity and dirty-state provenance. |
| `Stop` | `agent.message`, then `turn.completed` | Final message is direct. Completion outcome is usually inferred success; no structured hook outcome was observed. |
| `Interrupt` | `turn.completed` | Direct cancellation signal for the turn. Close unmatched tools as interrupted/unknown and emit a gap when needed. |
| `SessionEnd` | `session.stopped` | Direct stop boundary, but preserve the coarse provider reason rather than inventing a semantic reason. |
| Hook failure, queue overflow, unmatched start, or missing boundary | `capture.gap` | Direct local collector evidence. Never silently fabricate the missing activity. |
| `PermissionRequest` | NOT DIRECTLY AVAILABLE in the canonical schema | Keep as bounded adapter diagnostic until a later brief decides whether a provider-independent consent event is needed. |
| `PreCompact`/`PostCompact` | NOT DIRECTLY AVAILABLE | Can explain missing conversational context in diagnostics; not locally exercised. |
| `SubagentStart`/`SubagentStop` | NOT DIRECTLY AVAILABLE as a dedicated canonical event | May map to tool activity with provider metadata after Brief 01B validates payloads. |
| Intermediate agent messages/reasoning | NOT DIRECTLY AVAILABLE from the tested hooks | App Server snapshots contain richer agent/reasoning items, but this is optional enrichment rather than a hooks guarantee. |

Receiver timestamps are the only reliable timestamps for observed hooks because
their payloads had no event occurrence time. The adapter must keep `receivedAt`
and leave `occurredAt` absent rather than pretending they are the same.

## Session reconstruction experiment

The controlled request asked Codex to inspect a tiny Python project, reproduce a
failing unit test, fix the implementation, update a dependency file, delete an
obsolete file, add a notes file, rerun verification, and preserve a deliberately
pre-existing dirty change.

Using hooks plus the initial/final Git snapshots, a future analyzer could recover:

- the user's exact intent from `UserPromptSubmit`;
- the session, turn, project directory, and Git repository association;
- the important inspection and test commands;
- the first failed test output and later passing output;
- the patch action and final assistant summary;
- the exact final add/modify/delete set and diff from Git;
- the fact that one dirty change predated the session;
- the interrupted later command and its missing completion.

This is enough to explain the problem, the observed failure, the repair, and the
final implementation at useful learning-analysis quality. The reconstruction
still could not prove every file read, recover hidden reasoning, assign shell-made
changes to Codex versus a simultaneous user, obtain structured hook exit codes,
or distinguish all normal/idle/crash session-end reasons. Exact attribution
depends on the baseline snapshot, correlated provider events, and an explicit
uncertainty model.

App Server independently reconstructed the same completed coding turn with
better structured command and change status. That establishes its value as a
diagnostic reference and possible future reconciliation source, but the passive
polling and stability limitations prevent it from replacing hooks for V1.

### Minimum V1 data requirement

For the tested CLI, hooks plus Git meet the minimum with bounded compromises:
session and turn identity, receiver timestamps, repository context, user intent,
tool and command activity, final agent response, file changes and diff, observable
test/error/recovery evidence, turn interruption, and a normal session-end signal.
The compromises are timestamp precision, tool-dependent result parsing, coarse
end reasons, possible hook gaps, and uncertain concurrent-edit attribution.

## Risks and remaining unknowns

1. **Desktop remains unverified.** The installed application may share, transform,
   or omit CLI hooks and persisted threads. No passive-capture claim may be shown
   to users until the exact supported Desktop route is exercised.
2. **Client-version drift.** Results are exact for CLI 0.151.0. Brief 01B needs a
   supported-version range and a capability self-test, especially because 0.154.0
   was already available.
3. **Delivery gaps and ordering.** Async hooks may reorder or be cancelled; sync
   hooks add latency. Crashes and force kills may omit `SessionEnd`.
4. **Tool coverage varies.** Hosted web search and specialized paths may not emit
   the generic tool pair. Shell output is unstructured in observed hooks.
5. **Trust lifecycle is incomplete.** Safe merge, upgrade/retrust, conflict,
   removal, and retained-hash revocation need an installer prototype and manual
   UX validation.
6. **Session boundaries are coarse.** `SessionEnd.reason=other`, documented idle
   behavior, app switching, and simultaneous windows need explicit policy.
7. **Concurrent repository edits are ambiguous.** Git proves state changes but
   not actor attribution. Dirty/untracked baselines are mandatory.
8. **Performance is not production-proven.** The Python probe demonstrates the
   synchronous startup problem; it does not establish Rust helper targets under
   burst load or daemon outage.
9. **Cross-platform behavior is untested.** No Windows or Linux claim follows
   from this macOS Apple Silicon investigation.
10. **App Server passive reads may evolve.** Full hydration was deprecated while
    its replacement was experimental in the tested schema.

## Recommendation

Select **C. Hooks + Git hybrid**.

Build an isolated prototype, not production capture, around a minimal Rust hook
helper and a provider-independent `SessionSource` boundary. The helper should
validate a versioned input envelope, sanitize before any write, send a bounded
non-blocking local message, retain deterministic source IDs, and emit explicit
gap evidence. The prototype should take a consented Git baseline at session start
and a final snapshot at stop/end, preserving pre-existing dirty and untracked
state. It should implement only the evidence-backed mappings above.

Brief 01B should first run the same capability suite through the installed
Desktop client. It should then test hook install/merge/trust/update/remove UX,
duplicate and reordered delivery, daemon outage, queue overflow, malformed and
oversized payloads, sanitizer failure, crash/force-kill and idle end behavior,
multiple simultaneous sessions, dirty Git, shell-made edits, subagents,
compaction, and a supported-version change. It should establish strict helper
latency targets and failure visibility.

Keep App Server as an opt-in diagnostic/reconciliation experiment behind a
separate adapter. Do not depend on raw local storage and do not use
`thread/start`/`thread/resume` for the passive V1 workflow.

## G01 verdict

**CONDITIONAL GO.** On Codex CLI 0.151.0, trusted lifecycle hooks passively expose
enough intent, lifecycle, final response, tool, command, failure, recovery, and
interrupt evidence to reconstruct a useful real coding session. Git supplies the
independent baseline and exact final code changes that hooks cannot guarantee.
This works without making Mochi the Codex client and without bypassing Codex
trust.

The decision is conditional because Desktop execution is unverified, hook
timestamps/results/end reasons have real gaps, async reliability and production
latency are not yet proven, and safe trust/install lifecycle needs a prototype.
Mochi must not advertise passive Desktop capture until Brief 01B resolves those
conditions.
